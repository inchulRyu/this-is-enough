## 0. 왜 이 워크플로우인가

### 0.1 워크플로우 없이 작업할 때의 문제 — 이 스펙이 푸는 문제의 전부

1. **합의의 휘발.** 사용자와 대화하며 생긴 합의 사항과 다음 작업 목록이,
   대화가 길어질수록 컨텍스트에서 희석되거나 사라진다.
2. **코드베이스 재탐색.** 매 세션마다 에이전트가 코드베이스를 새로 훑는다.
   비효율적이고, 제대로 훑지 못해 잘못 이해하는 경우도 있다.
3. **작업 방식의 비일관.** 작업 방식이 획일화되어 있지 않아 결과를 신뢰하기 어렵다.

### 0.2 유행하는 하네스의 문제 — 이 스펙이 되풀이하면 안 되는 것

무겁다. 토큰을 많이 먹고 시간이 오래 걸리는데 결과가 그만큼 뛰어나지도 않다.

### 0.3 설계 기준

> **이름 그대로. 가볍지만, 필요한 것만 딱 존재한다.**

- 모든 요소(파일, 역할, 단계)는 0.1의 세 문제 중 하나를 직접 해결해야 존재 자격이 있다.
  해결하지 못하는 요소는 넣지 않고, v0.3에 있던 것이라도 뺀다 (§9).
- 에이전트가 문서를 읽는 비용도 비용이다. 모든 산출물은
  다음 에이전트가 판단·재개하는 데 필요한 최소량만 담는다.
- 승인·검증·문서화는 의식(ceremony)이 아니라 각각 한 번의 확인이다.

## 1. 핵심 개념 — 세 개의 머리를 동기화한다

이 워크플로우가 하는 일은 하나다. 다음 셋을 계속 동기화하는 것.

```text
사용자의 머릿속  ←→  에이전트의 이해  ←→  코드베이스의 실제 동작
```

- 동기화의 **수단은 문서**다. 합의는 요구사항 명세로, 시스템 이해는 지도로 남는다.
  문서에 없으면 동기화되지 않은 것이다.
- 동기화의 **확인 수단**은 두 가지다.
  구현 전에는 **사용자 승인**(사용자 머릿속과 일치하는지는 승인으로만 알 수 있다),
  구현 후에는 **검증**(코드가 승인된 흐름대로 동작하는지).
- 세 문제와의 대응: 합의의 휘발 → 요구사항 명세(§4),
  코드베이스 재탐색 → 헌법+지도(§3), 작업 방식 비일관 → 고정된 역할과 흐름(§5–§6).

핵심 철학은 v0.3에서 계승한다.

> Files are the source of truth. Not written, not remembered.

## 2. 불변식

깨지면 안 되는 약속. 이 스펙에서 가장 안 변하는 부분이다.

1. **합의는 문서에 있어야 존재한다.** 대화에서 나온 합의·결정·작업 항목은
   그 자리에서 요구사항 명세(또는 run log)에 기록한다.
2. **승인 없이 구현 없다.** 핵심 체크리스트가 사용자 승인을 받기 전에는
   구현을 시작하지 않는다.
3. **검증 pass 없이 완료 없다.** Verifier의 pass 없이는 어떤 작업도 완료가 아니다.
4. **동작·불변식·구조가 바뀌면, 지도 갱신 없이는 완료가 아니다.**
   값(리터럴)만 바뀐 변경은 지도를 건드리지 않는다.
5. **지도에 값을 적지 않는다.** 상수·임계값·필드 목록은 코드 포인터로만 가리킨다.
   포인터는 백틱 심볼 이름으로 쓰고 링크·줄번호는 쓰지 않는다 (Name, don't link).
6. **각 역할은 자기 산출물만 쓴다.** 남의 파일을 고치면 log에 이유를 남긴다.
7. **항상 더 나은 구조를 추구하되, 제안과 실행을 분리한다.**
   더 우월한 방식·구조를 발견하면 과감하게 제안한다(변경 비용을 두려워하지 않는다).
   단, 승인된 범위 밖의 실행은 하지 않는다.
8. **멈춤은 진짜 블로커 또는 완료에서만.** 오래 걸린다는 이유로 멈추지 않는다.

## 3. 헌법 + 지도 — 코드베이스 문서

문제 2(매 세션 재탐색·오독)를 푸는 장치. 사람이 코드를 기억하는 방식을 그대로 쓴다:
전체 동작 흐름과 단계별 기능, 대략적 위치만 기억하고, 세부 값은 그때그때 코드를 본다.

### 3.1 위치와 소유

- 기본 위치는 레포 루트의 `ARCHITECTURE.md`. 커밋되는 파일이다.
- 이미 존재하면 그 파일을 채택해 이 형식으로 점진 수렴시킨다.
- 생성·큰 개편은 사용자 확인을 받는다(이 문서 자체가 동기화 대상이므로).

### 3.2 내용 — 두 부분뿐

```md
# Architecture

<!-- 헌법과 지도만 담는다. 값(리터럴)은 코드 포인터로 강등한다.
백틱 심볼 이름만 쓰고 링크·줄번호는 쓰지 않는다. -->

## 헌법 — 왜, 그리고 깨지면 안 되는 것

### 불변식
- <교차 파일 불변식, 레이어 경계, 안전 약속. 예: "core는 adapters를 import하지 않는다">

### 설계 이유와 기각한 대안
- <왜 이렇게 만들었나. 왜 그 기능이 없나(의도된 부재)>

### 실패한 접근
- <시도 → 실패 이유 → 반복 금지. run 완료 시 여기로 승격된다>

## 지도 — 무엇이 어디서 일어나는가

### 전체 흐름
<입구에서 출구까지, 시스템의 주요 동작 흐름을 단계로. 각 단계는 한두 문장 + `심볼` 포인터>

### <영역>
<영역이 커질 때만 소절 추가. 이 영역의 흐름 + `심볼` 포인터. 배점·공식·값은 코드에>
```

- **헌법**은 코드를 아무리 읽어도 안 나오는 것만 담는다. 짧다(한두 페이지가 정상).
- **지도**는 흐름과 위치만 담는다. 문서 분량의 대부분이지만 얇다.
- 판별이 헷갈리면: *"누가 이 값을 코드에서 바꾸면 조용한 PR인가, 경보인가?"*
  경보면 헌법, 튜너블이면 코드(지도에 안 적음).
- 파일 분할(영역별 문서)은 한 파일이 실제로 비대해졌을 때만 한다. 기본은 한 파일.
  분할해도 규칙은 같다: 각 문서는 자기 고도만 말하고 한 칸 아래를 가리킨다.

### 3.3 갱신과 검사

- **갱신 트리거는 좁다.** 동작·불변식·구조가 바뀔 때만 손으로 갱신한다.
  리터럴 변경은 트리거가 아니다(포인터라서 갱신할 것이 없다).
- **run 안에서는 자동·증분이다.** verify pass 후 체크포인트 커밋 전에,
  이번 변경이 건드린 흐름·불변식만 갱신한다(§6, 불변식 4). `tie:map`은 run 밖의
  수동 진입점이다: 최초 생성, TIE 밖에서 코드가 바뀌었을 때의 재동기화,
  비대해진 지도의 재구성. 일상적으로 `tie:map`을 부를 일은 거의 없어야 정상이며,
  자주 부른다면 TIE 밖에서 작업이 많이 일어난다는 신호다.
- **검사는 싸게.** 지도를 읽거나 갱신하는 에이전트는 사용하는 백틱 포인터가
  실재하는지 grep으로 확인한다(rename으로 stale해진 포인터를 잡는다).
  테스트 하니스가 있는 레포는 헌법 불변식을 실제 테스트로 승격해도 좋다 — 선택 사항이다.
- **읽기 규칙.** 모든 역할은 코드베이스 전체를 훑기 전에 지도를 먼저 읽는다.
  지도가 가리키는 지점만 코드로 내려가서 본다.

### 3.4 지도의 의미

지도는 시간이 지나면 **사용자 머릿속 시스템 흐름의 서면 사본**으로 수렴한다.
매 run에서 사용자가 승인한 기대 흐름이 구현·검증을 거쳐 지도에 반영되기 때문이다.
그래서 검증(§5.4)은 "코드를 지도+체크리스트에 대조하는 일"이 된다.

## 4. 요구사항 명세 — 합의의 앵커

문제 1(합의의 휘발)을 푸는 장치. 용어: Spec → **명세**, Requirements → **요구사항**.

### 4.1 최상위 단계: 대화와 동기화

작업은 사용자와의 대화에서 시작한다. 이 단계의 일은 사용자 머릿속에 있는 것을
에이전트의 이해·코드베이스의 흐름과 동기화하는 것이다.

- 에이전트는 지도를 근거로 **현재 시스템의 동작 흐름**을 제시하고,
  요구사항이 반영됐을 때의 **변경 후 예상 흐름**을 제시한다.
- 사용자가 교정하면 즉시 문서에 반영한다.
- **대화 중 생긴 합의 사항과 구체 작업 목록은 그 자리에서 명세에 기록하고 계속 갱신한다.**
  대화가 길어져도 합의는 절대 컨텍스트와 함께 증발하지 않는다.
- 질문은 **아키텍처 blast radius가 큰 것부터** 한다. 답이 하위 결정을 가장
  크게 바꾸는 질문을 먼저 물어, 앞선 답이 이미 기록한 합의를 무효화하지 않게 한다.
- 모호한 요청("더 낫게")에는 열린 질문을 되던지지 않는다. 지도에 근거한 구체적
  해석 2~3개를 제시해 고르거나 교정하게 한다 — 한 번의 대화로 모호함을 없애고
  어휘를 맞춘다.

### 4.2 명세의 내용

```md
# 요구사항 명세

## 배경과 목표
<왜 이 변경이 필요한가, 무엇이 달성되어야 하는가. 몇 줄>

## 합의 사항
<!-- 대화 중 지속 갱신. 합의 즉시 추가. 구현을 구속하는 합의(기술 선택 포함)도 여기에 -->
- A-1: <합의 내용>

## 변경 후 기대 흐름
<이 요구사항이 반영된 시스템의 동작 흐름. 짧은 단계 서술. 사용자 언어로>

## 핵심 체크리스트
<!-- 가장 필수인 부분. 각 항목은 관찰 가능한 동작 흐름 하나 — "~하면 ~한다" 형태.
구현 방식·함수명·값은 쓰지 않는다. 이 목록이 검증의 기준이 된다. -->
- [ ] C-1: <흐름>
- [ ] C-2: <흐름>
- [ ] C-3: 기존 <인접 흐름>은 변경 없이 그대로 동작한다

## 제외 범위
- <이번에 하지 않는 것>

## 미결 질문
- 없음 <또는 시작을 막는 질문만>

## 승인
대기 | 승인됨 (<ISO 일시>)

## 갱신 기록
- <run 시작 후 추가된 합의는 여기에 일시와 함께 append>
```

### 4.3 승인

- 승인은 문서 리뷰 의식이 아니다. **핵심 체크리스트를 사용자와 같이 한 번 점검하고
  확인받는 것**이다. 체크리스트가 짧으면 승인도 한 번의 대답이다.
- 승인이 확인하는 것: 이 체크리스트가 사용자 머릿속의 기대 동작과 일치하는가.
  일치 여부를 아는 방법은 승인뿐이다 — 그래서 승인 없이는 구현이 없다(불변식 2).
- run 도중 새 합의가 생기면 `합의 사항`/`갱신 기록`에 append한다.
  체크리스트가 바뀌는 합의면 바뀐 항목만 다시 확인받는다.
- 승인을 기다리며 턴을 끝내게 되면 — 대화형 여부와 무관하게, 답이 올지는
  알 수 없다 — 끝내기 전에 블로커로 기록한다(`[블로커]`, `blocked=true`,
  `status=blocked`). 답(같은 세션 또는 `tie:resume`)이 오면 해제된다.
  질문만 남기고 상태를 안 쓰면 `state.json`이 run에 대해 거짓말하게 된다.

### 4.4 구현 명세는 위임한다

- 사용자는 구현 명세를 검토하지 않는다. 기술적인 면은 에이전트가
  리서치와 테스트로 스스로 검증할 수 있기 때문이다.
- 반드시 지켜야 할 구현 방법이 사용자와 합의됐다면 그것만 `합의 사항`에 명시한다.
- 나머지 구현 판단은 Planner의 방향 제시와 Implementer의 현장 판단에 맡긴다.

## 5. 역할

문제 3(작업 방식 비일관)을 푸는 장치. 네 역할이 고정된 순서로 일한다.
역할 이름은 상태 머신 단계와 정합한다: Planner(plan), Implementer(implement),
Verifier(verify), 그리고 Orchestrator. v0.3의 Generator·Evaluator는
실체에 맞게 개명했다 — 이름이 곧 단계다.

### 5.1 Orchestrator — 상태와 순서

메인 에이전트가 맡는 런타임 컨트롤러. 구현하지 않는다.

- 명세 승인 확인 → run 생성 → 역할 순서 진행 → 상태 갱신 → 중단/재개 판단 → 완료 처리.
- 각 역할 산출물이 존재하고 자기 역할에 맞는지 한 번 확인하고 넘어간다.
  깊이 읽는 것은 명백한 문제가 보일 때만.
- 서브에이전트 디스패치가 가능한 플랫폼에서는 항상 역할을 서브에이전트로 보낸다 —
  디스패치는 최적화가 아니라 기본값이고, 워크플로우 호출 자체가 위임 요청이다.
  인라인 수행은 디스패치 도구가 없을 때의 폴백일 뿐이다.
  디스패치 시 절대 경로(run 디렉토리, 명세, 지도)를 넘긴다.

### 5.2 Planner — 기술 방향

승인된 명세와 지도를 읽고 `plan.md`를 쓴다.

- **현재 레포 시스템의 전체 동작 흐름을 기준으로(제품 관점에서), 어떤 기술·접근으로
  구현하는 것이 좋을지 방향을 심층 조사해서 제시한다.** 필요하면 외부 리서치를 한다.
- 구현 상세는 쓰지 않는다. 코드 하나하나를 계획서에 쓰는 것이 아니다.
  함수명·파일 구조·스키마를 확정하지 않는다.
- 사용자와 이미 합의된 구체적 구현 방법이 있으면 그것은 명시한다(명세의 A-n 참조).
- 작업을 굵은 단위의 작업 항목(W-n)으로 나눈다. 체크리스트의 모든 C-n이
  어느 W-n에서 다뤄지는지 드러나야 한다.
- **단계별 계획.** 작업이 커서 여러 단계가 필요하면, 처음에는 단계 구획과
  각 단계의 목표만 잡고 **첫 단계의 W-n만 상세화**한다. 다음 단계는 앞 단계의
  verify pass 후, 그 시점까지 얻은 지식으로 시작 직전에 상세화해서 plan.md에
  append한다. 시작 시점의 추측으로 뒤 단계를 미리 확정하지 않는다.
  목표만 남긴 단계에도 그 단계가 커버할 C-n을 `covers:`로 표기해,
  모든 C-n이 어느 단계에서 다뤄지는지 항상 드러나게 한다.
- 더 나은 구조를 발견하면 계획에 제안으로 담는다. 승인된 범위를 바꾸는 제안이면
  블로커로 올려 사용자 결정을 받는다.

```md
# Plan

## 기술 방향
<조사 요약과 선택 이유. 시스템 전체 흐름(지도) 기준. 구현 상세 금지>

## 흐름 접목 지점
<지도의 어느 흐름·어느 단계에 접목되는지. `심볼` 포인터>

## 합의된 구현 방법
<A-n 중 구현을 구속하는 것. 없으면 "없음">

## 작업 항목
<!-- 작은 작업: W-n을 한 번에 나열. 큰 작업: 단계 제목 아래 묶고 첫 단계만
상세화하며, 다음 단계는 목표 한 줄(covers: C-n 표기 포함)만 남겼다가
시작 직전에 상세화해 append한다. -->
- [ ] W-1: <굵은 단위 작업> (covers: C-1, C-2)
- [ ] W-2: <...> (covers: C-3)

## Implementer 판단에 맡기는 것
- <파일 구조, 함수 경계, 테스트 방식 등>

## 검증 힌트
- <위험 지점, 영향 가능성 있는 인접 흐름>
```

### 5.3 Implementer — 구현

**코드를 가장 가까이서 마주하는 역할.** 세부 흐름을 전부 마주하는 것은 Implementer뿐이므로,
계획을 바탕으로 어떻게 구현할지 직접 판단하고 구현한다.

- Planner의 기술 방향은 따르되, 세부 구현은 스스로 더 나은 방향으로 진행한다.
  방향 자체가 현장에서 틀렸다고 판명되면 log에 남기고 Orchestrator에 돌려보낸다.
- 명세의 기대 흐름과 체크리스트를 벗어나지 않는다. 합의 사항(A-n)을 준수한다.
- 기존 레포의 구조·컨벤션을 존중하되, 더 나은 구조를 발견하면 log에 `[제안]`으로
  기록한다. 승인 없이 대규모 구조 변경을 하지 않는다(불변식 7).
- 작업 항목(W-n)을 진행하며 plan.md의 체크박스를 갱신하고,
  결정·실패한 접근·리스크를 log에 짧게 남긴다.
- 구현 요약과 Verifier가 봐야 할 지점을 log에 한 항목으로 남기고 넘긴다.
  diff·코드 블록·명령 출력 전문은 남기지 않는다.

**fix 규율** — verify fail을 받았을 때는 두 가지가 코드 수정보다 먼저다:

1. **진단이 수정보다 먼저.** 원인 가설을 나열하고, 검증 비용이 싸고 가능성이
   높은 순으로 확인해 원인을 증거로 확정한 뒤에 고친다. 원인 미확정 상태의
   추측성 수정은 하지 않는다 — 동일 실패 반복(§6의 reframe 승급 사유)의 주범이다.
2. **파급 나열이 수정보다 먼저.** 이 수정이 건드리는 흐름·호출자·상태를 log에
   나열하고 나서 고친다. recheck는 실패했던 C-n만이 아니라 이 나열을 우선
   점검한다 — fix가 새 결함을 만드는 것을 사후 발견이 아니라 구조로 막는다.

### 5.4 Verifier — 검증

핵심 역할: **사용자 머릿속의 동작 흐름대로 현재 코드가 동작하는지 체크하는 것.**
사용자 머릿속의 흐름은 이미 승인된 핵심 체크리스트에 있다.

1. **체크리스트 검증.** 각 C-n의 흐름이 실제로 그렇게 동작하는지 확인한다.
   실행해볼 수 있는 흐름은 실제로 실행해서 확인한다(테스트, 빌드, 런타임 시나리오,
   필요하면 E2E). 읽기만으로 때우지 않는다. 증거의 깊이는 위험에 비례시킨다 —
   문서 수정에 E2E를 돌리지 않고, 데이터·보안·결제에 정적 리뷰로 pass를 주지 않는다.
2. **전체 시스템 관점의 영향 점검.** 이 변경이 시스템의 다른 동작 흐름들을 깨지 않았는지
   확인한다. 지도의 흐름 목록이 점검 후보다. 접목 지점과 인접한 흐름을 우선 본다.
3. 결국 확인하는 것은 하나다: **전체 시스템이 사용자 머릿속의 동작 흐름과 일치하는가.**

**자세는 적대적, 앵커는 승인 범위.** 확인하려 하지 말고 깨뜨리려 해본다 —
각 C-n 흐름의 경계 입력과 그럴듯한 오용까지 실행해보고, 누락(모든 A-n 준수,
모든 C-n의 문자 그대로의 실행, 제외 범위 준수)을 사냥한다. 단 판정은 승인된
범위에만 앵커한다: C-n·A-n 위반과 인접 흐름 회귀만 fail 사유이고, 범위 밖
발견(리스크·개선 아이디어)은 `[제안]`으로 log에 남기며 판정에 섞지 않는다.
앵커 없는 적대적 리뷰는 매 run을 추측성 우려 더미로 끝낸다 — 그게 §0.2의 무거움이다.

```md
# 검증 보고

Verdict: pass | fail | blocked

## 체크리스트 검증
| 항목 | 방법 | 증거 | 결과 |
| C-1 | <실행/테스트/리뷰> | <한 줄 증거> | pass |

## 영향 흐름 점검
- <지도의 어느 흐름을 어떻게 점검했고 결과>

## 실패 상세
<!-- fail일 때만. 항목별로: 기대 / 실제 / 다음 조치 -->

## 다음 조치
- 없음 | <Implementer가 할 일>
```

- `fail`: 체크리스트 미충족, 인접 흐름 회귀, 관련 테스트/빌드 실패, 신뢰 불가한 통합.
  실패 항목마다 구체적 다음 조치를 남긴다.
- `pass`: 모든 C-n 충족 + 인접 흐름 무손상 + 심각한 이슈 없음.
- `blocked`: 사용자 결정 필요, 환경 문제, 반복 실패로 수렴 불가.
- **recheck 범위**: 실패했던 C-n + Implementer가 fix 전에 나열한 파급(§5.3
  fix 규율) + 관찰된 추가 접촉 지점. fix가 통과했던 C-n이나 지도의 흐름을
  깨면 새 실패로 기록한다.

## 6. 흐름과 상태 기계

```text
[대화]  동기화 → 명세 작성 → 핵심 체크리스트 승인          (tie:requirements)
[실행]  run 생성 → 지도 확인(없으면 생성 제안)              (tie:start)
        → plan (Planner)
        → implement (Implementer, W-n 단위)
        → verify (Verifier)
            fail → fix (Implementer) → recheck (Verifier)   * fix 한도 내 반복
                fix 소진·동일 실패 2회 → reframe (§6.1)      * 사이클당 3회
                    새 원인 확정 → fix 예산 리셋 → fix
                    사용자 결정 사안·새 프레임 없음 → 블로커
            pass ↓
        → 지도 갱신 (동작·불변식·구조가 바뀐 경우만)
        → checkpoint commit
        → 남은 작업 항목 있으면: 다음 단계가 목표만 있으면 plan(단계 상세화)으로,
          이미 상세화되어 있으면 implement로. 없으면 완료
[완료]  실패한 접근·새 불변식을 지도(헌법)에 승격
        → 종료 보고(explainer: 변경 전후 흐름 + 대신 내린 결정) + 선택적 이해 확인 퀴즈
```

- **단계 분할은 plan.md 안에서 한다.** 별도의 phase 디렉토리나 roadmap 파일은
  만들지 않는다. 기본은 한 호흡이고, 큰 작업은 단계(W-n 묶음)마다
  implement → verify → commit을 반복한다. 단계별 계획은 §5.2를 따른다:
  다음 단계는 앞 단계가 끝난 뒤, 그 시점의 지식으로 상세화한다.
- **체크포인트 커밋**: git이 있고 커밋이 허용되면 verify pass 후에 커밋한다.
  커밋 전 `git status --short`를 확인하고, 무관한 변경·의심 파일·시크릿이 보이면 멈춘다.
  volatile 상태(`.tie/`)는 스테이징하지 않는다. 이 run의 제품 변경과 지도 갱신은
  같은 체크포인트 커밋에 담는다 — 지도를 미커밋 상태로 남기지 않는다.
  커밋 불가 사유는 log에 남긴다.
- **fix 한도**: verify 사이클당 fix 루프 3회(verify pass마다 0으로 리셋 —
  단계별 run에서 앞 단계가 뒤 단계의 예산을 소진하지 않는다). fix 예산 소진
  또는 동일 실패 2회 반복은 곧장 블로커가 아니라 **reframe(§6.1)으로 간다** —
  더 고치기 전에 프레임부터 의심한다. reframe 경로까지 소진했을 때만 블로커로
  전환한다. 한도 도달은 포기가 아니라 에스컬레이션이다: 블로커 후 사용자가
  계속을 지시하면 두 카운터(`fix_loops`, `reframe_loops`)를 모두 리셋한다
  (동의가 예산을 갱신한다).
- **멈춤 조건**: 완료 / 사용자 결정 필요 / 환경 신뢰 불가 / 한도 초과 반복 실패 /
  위험·비가역 작업의 확인 필요. 이 다섯 가지뿐이다.

### 6.1 reframe — 프레임 재구성

fix 예산 소진과 동일 실패 반복은 "수정이 서툴렀다"보다 "프레임이 틀렸다"의
신호다 — 계획 방향 오류, 시스템 이해(지도) 오류, 요구사항 모순, 환경 불신 중
하나일 확률이 높고, 넷 다 같은 프레임 안의 fix로는 수렴하지 않는다. 곧장
사용자를 부르는 대신, 사람이 하는 동작을 제도화한다: **물러서서 문제를 다시
정의한다.** 정상 경로 비용은 0이다 — 이 단계는 실패 경로에서만 발화하므로
§0.2(무거움 금지)와 충돌하지 않는다. 지출은 한계 가치가 가장 높은 지점에만
생긴다.

- **독립성이 전부다.** Orchestrator는 신선한 컨텍스트의 렌즈 에이전트들을
  병렬 디스패치한다. 모든 렌즈 공통 금지: 막힌 run의 원인 가설·추론(믿음)은
  넘기지 않는다 — 실패한 **행동**을 알면 그 행동이 배제되지만, 실패한
  **믿음**을 알면 사고가 그 믿음에 앵커된다. 물려받은 가정에서 벗어나는 것이
  reframe의 존재 이유다.
- **렌즈 세 개 — 공개 수준은 렌즈별로 다르다** (우선순위 순, 플랫폼이
  허용하는 만큼 병렬로). 블라인드 렌즈는 탐색을, 이력 렌즈는 배제된 지형의
  회피를 보장한다 — 비용이 비대칭이므로(렌즈 하나의 헛돎 < 전원 앵커링에 의한
  reframe 전체의 조용한 실패) 오염되지 않은 눈 하나는 반드시 남긴다:
  1. **재정의 렌즈 — 완전 블라인드**: 증상·명세·지도만 받는다. 시도 이력은
     받지 않는다 — 행동 이력만으로도 낡은 프레임이 역추론되어 누설되고,
     이 렌즈의 존재 이유가 "처음부터 다시 도출"이기 때문이다. 실패한 C-n이
     애초에 검증 가능한지, 요구사항끼리 모순은 없는지까지 의심한다.
  2. **환경 회의 렌즈 — 이력 포함**: 증상·증거에 더해 시도한 것과 관찰된
     결과(사건이지 해석이 아님)를 받는다. 코드가 옳고 세상이 거짓말한다고
     가정 — 플레이키 테스트, 낡은 빌드, 캐시, 샌드박스 제약. 같은 실패의
     반복 패턴 자체가 이 렌즈의 원재료라 이력 없이는 일하지 못한다.
  3. **외부 렌즈 — 이력 포함**: 딥서치 — 라이브러리의 알려진 버그, 버전
     특이점, 같은 증상의 선례. 정확한 에러와 "안 통한 변경들"이 검색을
     조준한다. 웹 접근이 없으면 생략하고 log에 명시한다.
  서브에이전트 도구가 없으면 폴백: 사실만 다시 읽고 처음부터 재진단하는
  단일 인라인 패스를 수행하고, 독립성이 낮았음을 log에 남긴다.
- **산출물은 해답 또는 판정이다.** 최종 중복 제거는 렌즈가 아니라 전체
  이력을 가진 종합자의 몫이다: 블라인드 렌즈가 이미 시도·배제된 프레임을
  재제안하면 종합에서 걸러낸다(렌즈 하나의 낭비이지 실패가 아니다).
  Orchestrator가 렌즈 보고를 종합해 `[재정의]`로 log에 남기고 셋 중 하나로
  라우팅한다:
  1. **새 원인이 증거로 확정됨** → `fix_loops`를 리셋하고 확정된 원인과 함께
     fix를 재디스패치. 예산 갱신의 근거는 막힌 컨텍스트의 자기 평가가 아니라
     독립 증거다 — 이것이 자기 승인(fail-open)과의 차이다.
  2. **사용자 결정 사안**(요구사항 모순, 사용자만 고를 수 있는 트레이드오프)
     → 즉시 블로커. 에이전트를 더 불러도 사용자가 원하는 것은 조사로 알 수 없다.
  3. **새 프레임 없음** — 렌즈들이 이미 시도·배제된 프레임만 재생산 → 남은
     reframe 예산과 무관하게 즉시 블로커. 수렴하지 않는 reframe의 반복은
     무한 루프를 더 비싼 자리로 옮기는 것일 뿐이다.
- **한도: verify 사이클당 3회**(`reframe_loops`). 리셋 규칙은 fix와 동일 —
  verify pass 또는 블로커 후 사용자 동의. 한도의 의미도 같다: 진행도 측정이
  아니라, 사용자 확인 없이 자율로 쓸 수 있는 예산.
- reframe을 거쳐 도달한 블로커에는 정제된 분석이 담긴다: 시도한 프레임,
  배제된 가설, 남은 선택지와 권고. 이 구조의 목표는 사용자에게 도달하는
  블로커가 드물고, 도달했다면 전부 진짜 사용자급 결정인 상태다.

### 6.2 재개

1. `.tie/active_run` → run 디렉토리 해석
2. `state.json` → 현재 step과 owner
3. `log.md` 마지막 항목 → 직전 상황
4. 해당 step의 산출물(명세/plan/검증 보고) → 재개

`state.json`과 산출물이 어긋나면 산출물(사람이 읽는 쪽)이 아니라 `state.json`을
기계 상태의 기준으로 삼고, 어긋남을 log에 남긴 뒤 정정한다.

## 7. 파일 구조

```text
ARCHITECTURE.md            # 헌법 + 지도. 커밋 대상 (§3)
.tie/                      # 전체가 gitignore 대상 — 커밋되는 워크플로우 상태 없음
  active_run               # runs/<run-id> 포인터
  drafts/
    <draft-id>.md          # 승인 전 요구사항 명세 (단일 파일)
  runs/
    <run-id>/
      requirement.md       # 요구사항 명세 (§4) — 승인 상태 포함
      plan.md              # 기술 방향 + 작업 항목 (§5.2)
      verification.md      # 최신 검증 보고 (§5.4) — 덮어쓴다
      log.md               # append-only 저널 (아래)
      state.json           # 기계 재개 상태 (아래)
```

run 파일은 다섯 개뿐이다.

**log.md** — run에서 일어나는 모든 사건의 단일 저널. append-only.

```md
## <ISO 일시> [유형] <한 줄 제목>
<몇 줄 이내. 유형: 결정 | 진행 | 실패접근 | 제안 | 재정의 | 블로커 | 커밋 | 복구>
```

- `[결정]` 장기 영향이 있는 구현 결정과 이유
- `[실패접근]` 시도 → 실패 이유 → 반복 금지 (완료 시 헌법 승격 후보)
- `[제안]` 더 나은 구조·방식 제안: 내용, 이득, 대략적 변경 비용
- `[재정의]` reframe 종합: 동원한 렌즈, 제안된 프레임과 증거, 라우팅 결정
- `[블로커]` 막힌 이유, 선택지, 권고, 재개 조건

**state.json** — 최소 기계 상태.

```json
{
  "run_id": "2026-07-02-001-add-dashboard",
  "status": "in_progress",
  "step": "implement",
  "owner": "implementer",
  "current_item": "W-2",
  "approved_at": "2026-07-02T10:00:00+09:00",
  "fix_loops": 0,
  "reframe_loops": 0,
  "blocked": false,
  "next_action": "W-2 구현 후 Verifier 디스패치"
}
```

- `status`: `not_started | in_progress | blocked | completed | aborted`
- `step`: `plan | implement | verify | fix | reframe | map_update | checkpoint | complete`

**gitignore** — 규칙 하나로 끝난다.

```gitignore
.tie/
```

v0.3처럼 `.tie/` 내부를 선별 커밋할 필요가 없다. 커밋할 가치가 있는 것
(헌법+지도)은 처음부터 `ARCHITECTURE.md`에 있기 때문이다.

**run 규칙** (v0.3 계승, 축약): 하나의 독립 요구사항 = 하나의 run.
run id는 `YYYY-MM-DD-NNN-slug`. active run이 `in_progress`/`blocked`이면
새 run을 만들지 않고 기존 run의 명세에 갱신을 append한다. 완료된 run을
가리키는 active_run은 그대로 두고, 새 요구사항이 오면 새 run으로 덮어쓴다.
draft 승격 시 draft 파일을 run의 `requirement.md`로 복사·확인 후 draft를 지운다.

## 8. 진입점

진입점은 스킬 단일 계층이다. 별도의 커맨드(어댑터) 계층을 두지 않으며,
Claude Code(`/tie:...`)와 Codex(`$tie:...`)에서 이름이 동일하다.

| 진입점 | 역할 |
| --- | --- |
| `tie:requirements` | 대화·동기화·명세 작성·승인 (§4). run을 만들지 않는다 |
| `tie:start` | 승인된 명세(또는 즉석 요구사항)로 run 시작·완주. Orchestrator(§5.1)가 맡는다 |
| `tie:map` | `ARCHITECTURE.md` 최초 생성 · run 밖 변경 후 재동기화 · 지도 재구성. 사용자 확인을 거친다. run 중 갱신은 자동·증분(§3.3, §6)이므로 이 진입점이 필요 없다 |
| `tie:resume` | active run 재개 (§6.2) |
| `tie:status` | 읽기 전용 상태 요약 |
| `tie:doctor` | 상태 진단·안전 복구·v0.3 레이아웃 마이그레이션 |

역할 스킬(`tie:planner` · `tie:implementer` · `tie:verifier`)은 디스패치되는
역할 계약의 배달 수단이지 사용자 진입점이 아니다. Claude Code에서는
`user-invocable: false`로 피커에서 숨긴다(서브에이전트 호출은 유지된다).

즉석 요구사항으로 `tie:start`를 부른 경우에도 승인 게이트는 생략되지 않는다.
Orchestrator가 명세와 체크리스트를 만들어 **한 번** 확인받고 진행한다.

## 9. v0.3에서 제거·통합된 것

가벼움은 기능이다. 제거는 실수가 아니라 결정이며, 기준은 §0.1의 세 문제를
직접 풀지 못하는 요소는 두지 않는다는 것이다.

| v0.3 | v0.4 | 이유 |
| --- | --- | --- |
| `roadmap.md` + `phases/` 디렉토리 트리 | plan.md의 작업 항목(W-n) + 단계적 상세화(§5.2) | phase마다 디렉토리와 8개 파일은 구조 유지 비용이 효익을 넘는다. 단계별 계획·검증·커밋 경계 기능은 plan.md 안에서 유지된다 |
| `tasks.md` | plan.md의 체크박스 | 별도 파일이 필요할 만큼의 내용이 없다 |
| `validation_intent.md`, `validation_plan.md`, `verification_history.md` | `verification.md` 하나 | 검증 문서 3종은 검증을 좋게 만들지 않고 무겁게 만든다 |
| validation profile(`standard/high`) + L0–L5 enum | 원칙 한 줄: 증거는 위험에 비례, 실행 가능한 흐름은 실행해서 확인 | 분류 체계의 관리 비용 > 판단 보조 효과 |
| `decisions.md`, `changelog.md`, `retrospective.md`, `blockers.md` | `log.md` 단일 저널 | 네 파일의 구분 자체가 기록 비용. 유형 태그로 충분 |
| `current_state.md` + `run_state.json` | `state.json` | 인간용 요약은 log 마지막 항목이 대신한다 |
| `telemetry.jsonl` | 제거 | 세 문제 중 어느 것도 풀지 않는다. 필요해지면 확장으로 |
| `project_memory.md` | `ARCHITECTURE.md` 헌법의 "실패한 접근" | 제도적 기억은 헌법의 일부다. 파일 하나 감소, `.tie/` 전체 ignore 가능 |
| artifact quality gate 상세 절차 | Orchestrator의 한 줄 확인 | 얕은 확인이면 충분, 상세 규정은 스펙 무게만 늘린다 |
| RQ/CC/AD/EV 4종 ID 체계 | C-n(체크리스트), A-n(합의), W-n(작업) | 검증 기준이 체크리스트 하나로 통일됐으므로 ID도 하나면 된다 |

v0.3에서 그대로 계승한 것: 파일 우선 원칙, run 격리와 재개, 승인·확인이 필요한
위험 작업 목록, git 체크포인트 규율, fix 한도, doctor의 안전 원칙
(모호하면 멈춘다, 파괴적 복구 금지).

## 10. 사용하지 않는 경우

- 한 줄짜리 버그 수정. 그냥 고친다.
- 제품 동작이 안 바뀌는 순수 리팩터링. 체크리스트에 쓸 흐름이 없다.
- 일회용 스크립트. 워크스페이스가 아깝다.

단, 이런 작업에서도 `ARCHITECTURE.md`는 계속 유효하다. 동작·구조를 바꿨다면
run 없이도 지도를 갱신한다.

## 11. 안전 (v0.3 계승, 축약)

Orchestrator와 모든 역할은 다음을 하지 않는다: 프로젝트 밖 파일 수정,
시스템/네트워크 설정 변경, 확인 없는 파괴적 git 작업, 시크릿 읽기·기록·커밋,
Verifier pass 없는 완료 선언, 위험·비가역 작업의 무확인 진행.
해당 상황에서는 블로커로 멈춘다.

## 12. 마이그레이션 (v0.3 → v0.4)

`tie:doctor`가 담당한다. 원칙만 적는다.

- v0.3 run 레이아웃(`runs/<id>/`의 다수 파일)을 발견하면: 진행 중 run은 v0.3 규칙으로
  마저 끝내기를 권하고, 완료된 run은 그대로 둔다(읽기 전용 기록).
- `project_memory.md`가 있으면 내용을 `ARCHITECTURE.md` 헌법 섹션으로 승격하고
  원본은 백업으로 남긴다. 이 승격은 사용자 확인을 받는다.
- `.gitignore`의 v0.3 선별 규칙 세 줄은 `.tie/` 한 줄로 교체한다.
- 모호하거나 파괴적인 경우 항상 멈추고 묻는다.

## 13. 이 스펙 자체의 규율

이 스펙도 §3의 규칙을 따른다. §2(불변식)와 §0–§1이 헌법, §5–§8이 지도다.
파일 스켈레톤은 계약의 일부인 최소만 담고, 상세 문구는 skills가 소유한다.
skills는 이 스펙에서 파생되며, 런타임에 이 스펙을 읽지 않는다.
스펙과 skills가 어긋나면 스펙이 기준이고, 어긋남은 발견 즉시 고친다.
