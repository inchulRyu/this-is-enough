# 워크플로우 개편 노트 — 품질 앵커 · 3층 문서 모델 · 실험 모드

Status: draft — 생각 정리본이다. 아직 스펙이 아니며, runtime-spec / skills 반영은 별도 작업으로 진행한다.
Date: 2026-07-02

이 문서는 ThisIsEnough 워크플로우의 구조와 철학을 개편하기 위한 원칙 노트다.
세 개의 축으로 구성된다.

1. **품질 앵커** — 기능 품질의 기준을 구현 전에 사용자와 확정한다 (§1–§2)
2. **작업 태도** — 더 나은 구조의 추구 (§3), 대화 운영 (§4)
3. **지식 관리** — 코드베이스 문서의 3층 모델 (§5), 실험 모드 (§6)

> 본문의 코드 예시(`gate_a.qualify`, `SWING_SCHED_INTERVAL`, `core`/`adapters` 등)는
> 이 레포가 아니라, 이 모델을 처음 검토했던 외부 프로젝트(트레이딩 시스템)에서 가져온 것이다.

---

## 1. 전제 — "좋은 것"을 알아야 "안 좋은 것"을 알아본다

결과물을 보고 "안 좋다"고 판단할 수 있는 이유는 무엇이 좋은 것인지 명확히 알기 때문이다.
전문가가 더 까다로운 이유도 같다. 좋은 것이 어떤 것인지 더 명확하게 알고 있기 때문이다.

개발에서 이 "좋음의 기준"은 두 축으로 갈린다.

| 축 | 기준을 아는 주체 | 검증 방법 |
| --- | --- | --- |
| **기술적인 면** (구조, 구현 방식, 성능) | AI가 알 수 있다 | 리서치와 테스트를 통해 어떤 것이 더 좋은지 AI가 스스로 검증 가능 |
| **기능적인 면** (동작, 워크플로우, 경험) | 요구자만 안다 | 사용자가 직접 사용해보고 이상한 점을 지적해주기 전에는 검증 불가 |

기능적인 면은 요구자가 자신이 바라는 것을 명확히 알고 있을 가능성이 크다.
그러나 그 기준은 사용자가 검증해주기 전에는 시스템 안 어디에도 존재하지 않는다.

**따라서 기능적인 부분 — 특히 시스템의 워크플로우 — 는 구현 전에 확실하게 정해야 하고,
그 내용이 요구사항 명세서에 확실하게 기재되어야 한다.**

---

## 2. 요구사항 명세 — 기능 품질의 앵커

### 2.1 반드시 담는 것

- 이 요구사항을 반영했을 때 시스템의 **기대 동작(목표 동작)과 처리 흐름**
  (expected system behavior and workflow).
- **"구현됐을 때 이렇게 동작해야 한다"는 핵심 체크리스트** — Acceptance Criteria(수용 기준)에 해당한다.
- 이 체크리스트는 **사용자와 같이 점검하고 승인**받는다. 승인된 체크리스트가 이후 모든 검증의 기준이 된다.

명세는 이 시스템의 철학과 워크플로우를 준수한다.
요구사항 자체가 그것을 깨는 내용이라면 어쩔 수 없다 — 요구사항이 우선한다.

### 2.2 담지 않는 것 — 구현 명세는 위임한다

구현 명세서까지 사용자가 다 자세하게 검토할 필요는 없다.
기술적인 면은 AI가 스스로 검증할 수 있기 때문이다(§1).

- 구현 방식은 구현 에이전트가 알아서 판단한다. 필요하면 구현 에이전트가 구현 전에
  스스로 구현 명세서를 작성해서 사용한다.
- 반드시 지켜야 할 특정 구현 사항이 있으면, 그것만 요구사항 명세서에 명시한다.

### 2.3 용어

- Specification / Spec → **명세 / 작업 명세 / 요구사항 명세**
- Requirements → **요구사항**

## 3. 원칙 — 현재 코드에 집착하지 않기

**항상 더 나은 방식이나 구조를 추구한다.**

현재 구현된 구조에 너무 집착하지 않는다. 더 우월한 방식이나 구조가 있으면 과감하게 제안한다.
변경 비용을 두려워하지 않는다 — 대규모 변경을 감당하는 것이야말로 AI 에이전트가 하는 일이기 때문이다.

경계해야 할 실패 모드는 두 가지다.

1. 기존 구조나 방식으로도 가능하니까, 더 좋은 방식이나 구조를 **찾을 생각조차 안 하는 것**.
2. 찾아보고 발견했는데도 **제안하지 않는 것**.

항상 더 좋은 구조나 방식을 추구하고, 연구하고, 검색하고, 찾으면 과감하게 제안한다.

## 4. 대화 운영 — 결정된 작업 목록의 지속 갱신

요구사항을 다듬는 대화 중에는 **지금까지 결정된 구체 작업 목록을 계속 갱신**한다.
결정 사항이 대화 로그에 파묻히지 않게 하고, 언제든 현재 합의 상태를 한눈에 볼 수 있게 한다.

## 5. 코드베이스 문서화 — 헌법 + 지도 + 작은 검사층

코드베이스 구조 파악 문서의 참고 프레임: matklad ARCHITECTURE.md, arc42, C4.
결론부터: 문서를 **"헌법 + 지도(맥락) + 작은 검사층"** 으로 바꾼다.
값은 코드에 위임하고, 사람은 코드가 못 말하는 것만 손으로 쓰고,
문서↔코드 1:1은 *기억*이 아니라 *검사*가 강제한다.

### 5.1 문제 정의

문서와 스펙은 성격이 다른 정보가 한 파일에 섞이면 쉽게 비대해지고, 코드와 드리프트가 발생한다.
딜레마는 다음과 같다.

- **코드가 못 말하는 것** → 적을 가치가 분명히 있다 (유지)
- **코드가 이미 말하는 것(정확한 값들)** → 굳이 또 적을 필요 없다 (중복)
- **그렇다고 다 지우면** → 값 하나 찾으려고 코드 전체를 훑어야 하는 불편이 생긴다
- 그리고 이 1:1을 **검사(강제)** 하는 것이 가장 큰 이슈다

특히 값(리터럴)이 문서에 들어가는 순간 갱신 부담이 생기고, 그 부담이 드리프트 창을 만든다.

### 5.2 핵심 통찰 — 사람도 코드 값을 외우지 않는다

숙련자도 대규모 코드에서 정확한 값을 보려면 결국 코드를 하나하나 훑는다.
대신 숙련자의 머릿속에는 이것이 들어 있다.

1. 시스템 **전체 동작 흐름**
2. 각 동작 단계에 **어떤 기능들이 있는지**
3. 그것이 **어느 파일 / 어느 함수**였는지 — *대략적인 위치만*
4. 세부 값은 그때그때 **코드를 직접 본다**

이것이 가능한 이유: **"동작"을 외우는 것이 "코드 텍스트"를 외우는 것보다 쉽기 때문이다.**
내용물이 아니라 *무엇을 하는가*를 외우는 것이라서 그렇다.

그래서 문서도 같은 모양이어야 한다. 전부 기록하지 말고,
큰 틀(전체 흐름 + 단계별 기능 + 대략적 파일/함수 포인터)만 기록하고,
정확한 내용과 값은 코드에 맡긴다.

### 5.3 3층 모델

| 층 | 핵심 역할 | 내용 | 관리 방식 |
| --- | --- | --- | --- |
| **① 헌법**<br>왜 · 불변식 | 코드가 절대 말해주기 어려운 것 | 설계 의도, 교차 불변식, 의도된 부재, 레이어 경계, 기각한 대안 | 손글씨로 권위 있게 관리한다. 거의 변하지 않는다. 가능하면 enforcing 테스트 링크를 둔다. |
| **② 지도**<br>동작 · 포인터 | 각 단계가 무엇을 하고, 어디에 있는지 | 워크플로우 단계, 책임, 주요 심볼 이름, 코드 위치 포인터 | 손글씨로 작성하되 얇게 유지한다. **"Name, don't link"** — 백틱 심볼은 쓰되 링크·줄번호는 금지. |
| **③ 값**<br>리터럴 | 코드가 이미 말하고 있는 구체 값 | 상수, 임계값, DCF 가정, 점수 tier, 가격밴드, 라우트, 필드 목록 | 문서에 손으로 서술하지 않는다. 원칙적으로 포인터로 강등한다. 꼭 필요하면 코드에서 생성하거나 검사하게 한다. |

예시(외부 프로젝트):

- ① 헌법: "`core`가 `adapters`를 import하지 않음", "승인·전송 없이 주문 자동 발사 없음",
  "Gate A 산출은 `run_deep_research` 한 곳에서만", "주문 env 기본값은 `vps`"
- ② 지도: "장기우상향 자격 판정 → `gate_a.qualify`", "가격심사 → `gate_b.detect_entry`"
- ③ 값: "임계값 → `swing/core/gate_a.py`", "`SWING_SCHED_INTERVAL` → `config.py`"

**손으로 쓰는 문서는 ① 헌법 + ② 지도 딱 둘이다.**
③ 값은 코드에 위임하고 문서에는 포인터만 남긴다. 그리고 그 1:1 대응은 사람의 기억이 아니라
문서 밖의 **작은 검사층(테스트)** 이 강제한다. 그래서 문서는 무거워지지 않는다.

- **① 헌법**은 "왜 이렇게 설계했는가"와 "절대 깨지면 안 되는 약속"을 다룬다.
  코드를 아무리 읽어도 안 나오는 유일한 정보라서 문서로 남길 가치가 가장 크다.
  분량은 짧다 — 한두 페이지. 가장 안 썩고 가장 값지다.
  - 약속의 예: "주문은 사람 승인 없이 자동 발사 안 된다", "코어는 어댑터를 안 가져온다"
  - 왜의 예: "두 게이트로 나눈 이유 = 자격과 타이밍의 분리",
    "승인 큐를 따로 *안* 만든 이유 = 1인 도구라 과잉" (의도된 부재)
- **② 지도**는 "무엇이 어디에 있는가". 시스템의 동작 흐름과 주요 구현 지점을 연결해주는
  얇은 안내서다. 문서 분량의 대부분이 이것이다.
- **③ 값**은 코드가 이미 알고 있는 리터럴. 문서에 직접 적는 순간 코드와 어긋날 가능성이 커진다.

### 5.4 재귀적 zoom — 같은 모양이 층층이

모든 영역 문서는 같은 모양이다. 각자 영역의 **헌법(왜·약속) + 지도(흐름·기능·위치)**.
그리고 그 위에 시스템 전체 지도가 한 장 더 있다. 구조는 트리다.

```text
README.md          ← Level 0 : 시스템 전체 동작 흐름 + 서브시스템 지도
  └ <area>.md      ← Level 1 : 이 영역의 흐름 + 함수 포인터
      └ 함수 이름   ← Level 2 : 이름이 가리키는 곳 (심볼 검색으로 도달)
          └ 코드    ← 바닥    : 값 · 공식 · 디테일 전부
```

규칙은 매 층 똑같다 — **자기 고도만 말하고, 한 칸 아래를 가리킬 뿐, 아래 디테일을 반복하지 않는다.**

- 위(README)는 "관문 단계가 있고 자격·타이밍을 본다, 자세한 건 영역 문서로" 까지만.
  하위 문서의 세부 영역 목록을 반복하지 않는다.
- 영역 문서는 "Gate A는 `qualify`에서 8개 영역으로 판정한다" 까지만.
  8개 영역의 배점·공식은 반복하지 않는다(코드에 있다).
- 이것이 안 지켜지면 한 층 위에서 똑같은 중복 문제가 또 생긴다. **고도 규율이 전부다.**

이건 새로운 발명이 아니라 C4 모델의 "zoom 가능한 지도"(시스템 → 부분 → 코드)이고,
전문가가 코드를 외울 때 쓰는 top-down 방식 그대로다.

### 5.5 ①↔③ 경계 휴리스틱

가장 헷갈리는 경계는 "이 값이 헌법인가, 튜너블인가"이다. 판별 질문:

> **"누가 이걸 코드에서 바꾸면 — 조용한 루틴 PR이어야 하나, 경보가 울려야 하나?"**

- **경보가 울려야 한다** (예: 주문 기본 env=`vps`, `core` ↛ `adapters`) → **① 헌법**
- **튜너블이다** (예: 종목당 주문 상한, 점수 가중치) → **③ 값** (코드에)

### 5.6 검사층 — 검사는 "의미적"이어야 한다

기성 위키 lint(끊긴 링크·인용 해소)는 *내부 정합성*만 본다.
필요한 것은 **문서값 == 코드값** 검사이며, 작지만 직접 만들어야 한다.

1. **리터럴 검사**: 문서에 남는 극소수 인라인 값에
   `<!-- check: swing.config.SWING_SCHED_INTERVAL -->` 태그를 달고,
   import해서 doc == code를 단언하는 테스트.
2. **심볼 존재 검사**: ② 지도의 백틱 포인터가 실재하는지 검사한다
   (rename으로 포인터가 stale해지는 것을 잡는다). AST/import로 싸게 가능하다.
3. **불변식 = 아키텍처 테스트**: ① 헌법의 핵심 불변식 상당수는 *실행 가능*하다.
   "core가 adapters를 import하지 않음"은 grep 테스트로,
   "Gate A 산출 경로는 1곳"은 호출그래프 테스트로 강제한다.
   → **산문은 "왜"를 적고, 테스트가 "여전히 참"을 강제한다.**
   기존 conformance 문서가 있다면 기계적으로 검증 가능한 항목만 실제 테스트로 승격하면 된다.

### 5.7 이득 — 갱신 트리거가 줄어든다

- 지금: **리터럴 하나 바뀌어도 문서를 손봐야 한다.** 이 부담이 드리프트 창을 만든다
  (스펙 갱신이 0회인 구간이 git 히스토리에 실재한다).
- 바뀜: **리터럴만 바뀌면 문서를 손댈 필요가 0이다** (포인터라서).
  검사 테스트가 빨개지면 그때만 본다. **동작·불변식·구조가 바뀔 때만** 손글씨를 쓴다.
- 결과: 유지보수 표면이 급감하고 드리프트 창이 닫힌다.

### 5.8 "완료의 정의"에 이해를 강제한다

규칙: **"코드만 바꾸고 명세 미갱신 = 미완성."**

이 규칙은 *내가 설명하지 못하는 변경은 출시하지 못하게* 만드는 forcing function이다.
"임계치는 바꿨는데 왜, 어디까지 영향이 가는지 모름" 부류의 실수를 잡는다.

### 5.9 코드가 못 말하는 것 — 명세의 금맥

- **여러 파일을 가로지르는 불변식**: "Gate A를 산출하는 경로는 `run_deep_research` 단 1곳",
  "모든 상태 write는 `apply_state`/`set_action_override`로 흐른다" —
  어떤 단일 소스 파일도 이것을 명시하지 않는다. 명세만이 그것을 담는다.
- **제도적 기억**: 규칙 개정 이력(v1.0→v1.1), right-size 결정 같은 것은 코드엔 영원히 안 남는다.
- **의도된 부재**: 왜 그 기능이 *없는지*는 코드를 아무리 읽어도 안 나온다.

### 5.10 근거 (조사 요약)

**(a) 이 모델은 이미 이름이 붙은 표준 관행이다**

- **matklad 「ARCHITECTURE.md」** (2021, rust-analyzer에서 유래):
  "가장 큰 병목은 코드를 쓰는 게 아니라 어디를 고칠지 찾는 것" → 문서는 조감도 + codemap이어야 한다.
  **"Name, don't link"** — 중요한 파일·모듈·타입의 *이름*을 적되 하이퍼링크·줄번호는 금지
  (링크는 썩는다); 백틱 심볼로 심볼 검색을 유도한다. "자주 안 바뀌는 것만 적어라.
  코드와 동기화하지 마라." ← "대략적 위치 포인터"의 정식 명칭.
- **C4 모델**: "코드의 구글 지도". 최하단 코드 레벨은 *선택적이며 장기 문서로는 비권장,
  IDE로 자동 생성* = "디테일은 코드에서". (arc42도 같은 계열의 참고 프레임)

**(b) "동작이 텍스트보다 외우기 쉽다"는 인지과학에 근거가 있다**

- **Naur, 「Programming as Theory Building」(1985)**: 프로그래밍의 본질 산출물은 프로그래머
  머릿속의 "이론(theory)"이고, 텍스트·문서는 부차물이다. 실제 컴파일러 사례에서 *"전체 프로그램
  텍스트와 추가 문서조차 설계의 깊은 통찰을 전달하기에 불충분"*했다.
  → **코드값을 빠짐없이 복제해도 정작 중요한 것(설계)은 안 넘어간다.** 전수복제 전략의 근거를 정면으로 깬다.
  또한 동작 흐름보다 **"왜"(의도·제약·기각한 대안)** 가 더 값지다 — 그것이 코드가 절대 못 말하는
  최고가치 잔여물이다.
- **프로그램 이해 연구** (Brooks; von Mayrhauser & Vans; Wiedenbeck, Gellenbeck & Cook):
  전문가는 코드를 다 읽지 않는다. 외부 단서로 **가설**을 세우고 **beacon**(고수준 기능을 가리키는
  단서, 특히 이름)을 스캔해 확인한다. 청킹으로 하위 디테일은 **라벨로 치환**된다.
  이름이 지식으로 들어가는 인덱스 역할을 한다는 것은 경험적으로 입증됐다. ← 포인터가 곧 beacon이다.
- **체스 청킹** (Chase & Simon 1973; Gobet & Simon): 고수의 우월한 기억은 말 하나하나의 암기가
  아니라 LTM에 저장된 수천 개의 의미 있는 **chunk(패턴 덩어리)** 인식에서 온다.
  ← "전문가는 의미 있는 패턴으로 항해하지, 축자적 디테일로 항해하지 않는다"의 원천.

**(c) 문헌이 이 모델을 다듬는 3지점**

1. **지도는 "오리엔테이션"용이다** (Corritore 실측: 편집이 시작되면 코드가 문서를 대체,
   문서 접근 0.88 → 0.18). → "디테일은 코드에서"를 입증하고, **값 복제는 효용 0에 드리프트 비용만**
   남긴다는 뜻. 단, *왜/불변식*까지 지우면 안 된다.
2. **Naur 보강**: 동작 흐름보다 "왜"가 더 값지다 (위 참조).
3. **Diátaxis**: 이 문제의 정체는 *타입 혼동*이다 — **explanation**(왜·서사 = 손으로 씀)과
   **reference**(상수·라우트 = 생성/검사)를 한 파일에 섞은 것.
   꼭 남겨야 할 값은 손 동기화가 아니라 **코드에서 생성/검사**한다 (= "검사" 이슈의 정답).

**(d) AI 에이전트가 정비하는 레포라서 더 그렇다**

- 에이전트는 "가서 코드 읽어"의 비용이 인간보다 싸다 → **포인터 전략이 인간보다 더 유리하다.**
- 단, 에이전트는 stale 값을 더 잘 믿는다 → 문서에 남는 소수 값은 **반드시 생성/검사로 못박아야** 한다.
- 새 세션을 시작하는 에이전트는 매번 100여 개 소스에서 시스템 동작을 다시, 그것도 손실적으로
  유도해야 한다. 큐레이션된 권위 명세는 **정확한 시스템 상태를 컨텍스트 창에 싸게 적재하는
  가장 좋은 수단**이다. → 일반 레포보다 명세의 ROI가 구조적으로 높다.

## 6. 실험 모드

리서치·튜닝처럼 결과가 가설의 검증인 작업을 위한 별도 모드다.

### 6.1 실험 전 — 가설 수립

매 실험 시작 전에 가설을 세운다. 이번 실험은 어떤 가설로 진행하는가를 명시한다.

가설의 재료:

- 관련 기술들을 심층 조사해서 반영해볼 만한 내용을 찾는다.
- 지난 실험들의 내용으로부터 아이디어를 도출한다.
- 조사에서 찾은 내용과 지난 실험 결과 사이의 융합 여지를 확인한다.
- 항상 새로운 방법의 도입을 적극적으로 고민한다.

새로운 방법에 대한 규율:

- 한 번 해봤을 때 안 좋다고 바로 버리지 않는다. 구현 미숙인지, 파라미터 조정이 필요한 상태인지,
  정말 가망이 없는 것인지는 **심층 연구와 여러 번의 시도**로만 판별된다.
- 현재의 구조·방법·구현을 버리는 것에 주저하지 않는다 (§3과 같은 원칙).

### 6.2 실험 후 — 증거 기반 원인 규명

이번 실험 결과에 대한 **정확한 원인을 반드시 찾아낸다.**
왜 이런 결과가 나왔는지 짐작하는 것이 아니라, 정확한 증거를 바탕으로 정확한 원인을 찾는다.

- 어떤 구현 때문에 이 결과가 발생했는지.
- 그 구현 내용이 왜 이런 결과를 초래했는지 심층 조사.
- 그렇게 찾은 원인을 어떻게 해결할지 도출.

### 6.3 적대적 검증

매 실험 후 **적대적 검증 에이전트 3개**를 호출해서 실험(설계·실행·해석)을 리뷰한다.
